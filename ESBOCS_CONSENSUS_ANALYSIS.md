# Анализ инициализации ESBocs консенсуса в Cellframe SDK

## Обзор

ESBocs (Efficient Stake-Based Ordered Consensus System) - это консенсусный механизм для блокчейн цепей в Cellframe SDK. Этот документ описывает процесс инициализации, условия активации и причины, по которым консенсус может не запуститься.

## Файлы кода

- **Основной файл**: `cellframe-sdk/modules/consensus/esbocs/dap_chain_cs_esbocs.c`
- **Заголовочный файл**: `cellframe-sdk/modules/consensus/esbocs/include/dap_chain_cs_esbocs.h`

## Процесс инициализации консенсуса

### 1. Вызов callback функции `s_callback_created`

Функция `s_callback_created` вызывается автоматически при создании блокчейн цепи. Это происходит в момент загрузки цепи после старта ноды.

**Расположение**: строки 550-683

### 2. Последовательность проверок в `s_callback_created`

#### Шаг 1: Проверка сертификата для подписи блоков (строки 572-591)
```c
const char *l_sign_cert_str = dap_config_get_item_str(a_chain_net_cfg, DAP_CHAIN_ESBOCS_CS_TYPE_STR, "blocks-sign-cert");
dap_cert_t *l_sign_cert = dap_cert_find_by_name(l_sign_cert_str);
```

**Что требуется:**
- Конфигурация должна содержать параметр `blocks-sign-cert` с именем сертификата
- Сертификат должен существовать и быть загруженным
- Сертификат должен содержать приватный ключ (`enc_key->priv_key_data`)

**Ошибки:**
- `-1`: Сертификат не найден
- `-2`: Сертификат не имеет приватного ключа
- `-3`: Сертификат не указан в конфигурации

**Критичность**: ВЫСОКАЯ - без сертификата консенсус не запустится

#### Шаг 2: Проверка роли ноды (строки 592-598)
```c
dap_chain_node_role_t l_role = dap_chain_net_get_role(l_net);
if (l_role.enums > NODE_ROLE_MASTER) {
    log_it(L_NOTICE, "Node role is lower than master role, so this node can't be a consensus validator");
    return -5;
}
```

**Что требуется:**
- Роль ноды должна быть MASTER или выше (ROOT)

**Ошибки:**
- `-5`: Роль ноды ниже MASTER

**Критичность**: ВЫСОКАЯ - только MASTER/ROOT ноды могут быть валидаторами

#### Шаг 3: Проверка делегирования ключа (строки 599-613)
```c
if (!l_esbocs_pvt->poa_mode) {
    if (!dap_chain_net_srv_stake_key_delegated(&l_my_signing_addr)) {
        log_it(L_WARNING, "Signing key is not delegated by stake service. Switch off validator mode");
        return -6;
    }
}
```

**Что требуется:**
- Ключ подписи должен быть делегирован через stake service (если не PoA режим)
- Или ключ должен быть в списке PoA валидаторов (если PoA режим)

**Ошибки:**
- `-6`: Ключ не делегирован через stake service
- `-7`: Ключ не в списке PoA валидаторов

**Критичность**: ВЫСОКАЯ - без делегирования консенсус не запустится

#### Шаг 4: Загрузка validator orders из GDB (строки 638-667)
```c
char *l_gdb_group_str = dap_chain_net_srv_order_get_gdb_group(l_net);
size_t l_orders_count = 0;
dap_global_db_obj_t * l_orders = dap_global_db_get_all_sync(l_gdb_group_str, &l_orders_count);
```

**Что происходит:**
1. Получается GDB группа для orders
2. Загружаются все orders из GDB через `dap_global_db_get_all_sync`
3. Ищется order, который:
   - Имеет `srv_uid == DAP_CHAIN_NET_SRV_STAKE_POS_DELEGATE_ID`
   - Подписан ключом валидатора (`dap_pkey_compare_with_sign`)
   - Используется самый свежий order (по `ts_created`)

**Что требуется:**
- GDB должен быть синхронизирован
- В GDB должны быть validator orders
- Должен быть order, подписанный ключом текущего валидатора

**Ошибки:**
- `-4`: Не найден валидный order для валидатора
  ```c
  if (IS_ZERO_256(l_esbocs_pvt->minimum_fee)) {
      log_it(L_ERROR, "No valid order found was signed by this validator delegated key. Switch off validator mode.");
      return -4;
  }
  ```

**Критичность**: КРИТИЧЕСКАЯ - без orders консенсус не активируется

#### Шаг 5: Запуск таймера консенсуса (строки 674-681)
```c
dap_chain_add_callback_notify(a_chain, s_new_atom_notifier, l_session->proc_thread, l_session);
dap_proc_thread_callback_add(l_session->proc_thread, s_session_round_new, l_session);
l_session->cs_timer = !dap_proc_thread_timer_add(l_session->proc_thread, s_session_proc_state, l_session, 1000);
DAP_CHAIN_PVT(a_chain)->cs_started = true;
```

**Что происходит:**
- Регистрируется callback для новых атомов (блоков)
- Планируется создание нового раунда (`s_session_round_new`)
- Запускается таймер консенсуса (вызывается каждую секунду)
- Устанавливается флаг `cs_started = true`

### 3. Создание нового раунда (`s_session_round_new`)

**Расположение**: строки 1163-1250

**Что происходит:**
```c
a_session->cur_round.id++;  // Увеличивается round_id
a_session->cur_round.sync_attempt++;
a_session->state = DAP_CHAIN_ESBOCS_SESSION_STATE_WAIT_START;
```

**Важно:**
- `round_id` увеличивается, но начальное значение может быть 0
- Отправляется сообщение START_SYNC другим валидаторам
- Состояние меняется на `WAIT_START`

### 4. Расчет реального round_id (`s_session_calc_current_round_id`)

**Расположение**: строки 1278-1333

**Когда вызывается:** Только когда достаточно валидаторов синхронизировано (строка 1594)

**Что происходит:**
```c
// Проходит по всем валидаторам
for (dap_list_t *it = a_session->cur_round.all_validators; it ;it = it->next) {
    dap_chain_esbocs_validator_t *l_validator = it->data;
    if (!l_validator->is_synced)  // Пропускает несинхронизированных
        continue;
    
    // Ищет START_SYNC сообщение от этого валидатора
    // Извлекает round_id из сообщения
    l_id_candidate = l_item->message->hdr.round_id;
}

// Выбирает round_id, который предложен большинством валидаторов
```

**Критичность:** 
- `round_id` устанавливается только когда `minimum validators are synchronized` (строка 1594)
- Если недостаточно синхронизированных валидаторов - `round_id` остается 0

## Критические условия для активации консенсуса

### 1. **Validator Orders в GDB**
- ✅ Orders должны быть созданы и сохранены в GDB
- ✅ Orders должны быть синхронизированы между нодами
- ✅ Должен быть order, подписанный ключом валидатора
- ❌ Если orders отсутствуют → return -4 → консенсус не запускается

### 2. **Синхронизация валидаторов**
- ✅ Минимальное количество валидаторов должно синхронизироваться
- ✅ Валидаторы должны обменяться START_SYNC сообщениями
- ✅ Для расчета `round_id` нужны сообщения от синхронизированных валидаторов
- ❌ Если недостаточно синхронизированных → `round_id` остается 0

### 3. **Сетевые связи**
- ✅ Валидаторы должны иметь активные сетевые связи
- ✅ Сообщения START_SYNC должны передаваться между валидаторами
- ❌ Если связи не установлены → синхронизация невозможна

### 4. **Таймер консенсуса**
- ✅ Таймер должен быть активен (`cs_timer != 0`)
- ✅ Таймер вызывается каждую секунду для обработки состояния
- ❌ Если таймер не запущен → консенсус не работает

## Что может остановить консенсус

### На этапе инициализации (`s_callback_created`):

1. **Отсутствие сертификата** (`-1`, `-2`, `-3`)
   - Сертификат не указан в конфигурации
   - Сертификат не найден
   - Сертификат не имеет приватного ключа

2. **Неправильная роль ноды** (`-5`)
   - Нода имеет роль ниже MASTER

3. **Ключ не делегирован** (`-6`, `-7`)
   - Ключ не делегирован через stake service
   - Ключ не в списке PoA валидаторов

4. **Отсутствие validator orders** (`-4`) ⚠️ **САМАЯ ЧАСТАЯ ПРОБЛЕМА**
   - Orders не созданы
   - Orders не синхронизированы в GDB
   - Order не подписан ключом валидатора
   - GDB не синхронизирован до инициализации цепи

### На этапе синхронизации раунда:

1. **Недостаточно синхронизированных валидаторов** (строка 1593)
   ```c
   if (l_min_validators_synced >= PVT(l_session->esbocs)->min_validators_count && !l_round_skip) {
       l_session->cur_round.id = s_session_calc_current_round_id(l_session);
   }
   ```
   - Если `validators_synced_count < min_validators_count` → `round_id` не устанавливается
   - `round_id` остается 0 или предыдущим значением

2. **Отсутствие START_SYNC сообщений**
   - Валидаторы не отправляют START_SYNC сообщения
   - Сетевые связи не установлены
   - Сообщения теряются в сети

3. **Неактивный таймер консенсуса**
   ```c
   if (!l_session->cs_timer)
       return; // Timer is inactive
   ```
   - Таймер остановлен или не запущен
   - Консенсус не обрабатывает состояние

## Временная последовательность инициализации

```
1. Цепь загружается → s_callback_created вызывается
2. Проверки (сертификат, роль, делегирование)
3. Загрузка orders из GDB через dap_global_db_get_all_sync
4. Если orders найдены → запуск таймера консенсуса
5. s_session_round_new планируется через callback
6. Отправка START_SYNC сообщений
7. Ожидание синхронизации валидаторов
8. Когда достаточно синхронизировано → s_session_calc_current_round_id
9. round_id устанавливается > 0
10. Консенсус готов к созданию блоков
```

## Проблема с round_id = 0

### Причины:

1. **GDB не синхронизирован до инициализации цепи**
   - ESBocs инициализируется при загрузке цепи
   - Если GDB не синхронизирован → orders не найдены → return -4
   - Консенсус вообще не запускается

2. **Orders найдены, но валидаторы не синхронизированы**
   - Консенсус запускается (`cs_started = true`)
   - Но `round_id` не устанавливается
   - Остается 0 до тех пор, пока не синхронизируется минимум валидаторов

3. **Сетевые связи не установлены**
   - START_SYNC сообщения не передаются
   - Валидаторы не могут синхронизироваться
   - `round_id` не может быть рассчитан

## Рекомендации для stage environment

### 1. Критический порядок операций:

```
1. Создать validator orders
2. Сохранить orders в GDB
3. Синхронизировать GDB между всеми нодами
4. ДОЖДАТЬСЯ завершения синхронизации GDB
5. Только потом загружать цепи (чтобы ESBocs мог найти orders)
```

### 2. Проверки перед инициализацией цепи:

- ✅ GDB синхронизирован
- ✅ Orders присутствуют в GDB на всех нодах
- ✅ Сетевые связи установлены
- ✅ Все валидаторы ONLINE

### 3. Ожидание активации консенсуса:

- ✅ Проверять `round_id > 0` (не просто наличие orders)
- ✅ Ждать достаточно времени для синхронизации валидаторов
- ✅ Проверять статус ESBocs через `esbocs status`

## Выводы

1. **ESBocs инициализируется при загрузке цепи**, а не при старте ноды
2. **Validator orders ДОЛЖНЫ быть в GDB ДО загрузки цепи**, иначе консенсус не запустится
3. **round_id устанавливается только после синхронизации валидаторов**, а не сразу при инициализации
4. **Синхронизация валидаторов требует активных сетевых связей** и обмена START_SYNC сообщениями
5. **Таймер консенсуса должен быть активен** для обработки состояния и синхронизации

## Следующие шаги для исправления проблемы

1. Убедиться, что GDB синхронизирован ДО загрузки цепи
2. Проверять наличие orders в GDB перед инициализацией цепи
3. Ждать синхронизации валидаторов перед проверкой `round_id`
4. Увеличить timeout для синхронизации валидаторов
5. Добавить дополнительные проверки сетевых связей между валидаторами
